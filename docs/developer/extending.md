# 扩展与维护

新增功能先说明“美术想改变什么”和“当前功能缺少什么”，再决定代码放在哪里。不要为了和 lilToon 功能列表一致而拆改已有模块。

1. 核对当前源码、契约和真实资产。列出功能状态、输入数据、控制粒度与依赖。
2. 设计兼容参数：稳定 ID、视觉含义、单位、默认值、硬范围和推荐范围。已有底层选项继续保留；不改变旧 ID 含义。
3. 为每个后端说明映射方法、支持条件和误差。Unsupported 指明究竟哪个接口/范围不支持，不把局部限制说成整体不可能。
4. Runtime 放数据与运行逻辑，Editor 放工具与保存。新资产只修改本项目拥有的资源；避免改引擎或第三方原资源。
5. 更新功能页、参数映射、状态清单和[更新记录](../changelog.md)，重新生成参考表。
6. 执行适用的编译、数据和画面验证；记录环境、日期、证据和未测试项。最后构建文档。

## Outline 扩展示例

若新增宽度控制，需同时检查 `FNPROutlineSettings` 的默认值、UPROPERTY 编辑依赖、`Validate`、相等比较、`FNPROutlineOverride::Apply`、区域来源说明、MID 绑定、材质节点及预设读写。MID 是可在运行时修改的材质实例。只加 UI 滑条无法证明这些环节都接通。

新算法不要复用含义不同的 `WidthPixels` 或 `HullWidthCm`；像素和厘米不可无条件等价。扩展 Section 支持前要解决共享槽与多 LOD 身份问题。LOD 指随距离切换的不同精细程度网格；它们的 Section 编号未必对应同一区域。

## 长期规则

仓库根 `AGENTS.md` 是后续开发任务的维护入口。人写的视觉说明和流程由开发者更新，自动表负责客观数据。历史报告留在 `Documentation/`，新页面链接它们的证据或解释摘要。真实截图缺失时写“待补”，不使用生成图充当渲染验证。
