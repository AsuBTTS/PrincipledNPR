# 项目开发说明与约束

更新日期：2026-10-22。本文供后续开发使用：先确定改动属于哪个部分，再按对应约束实现和验证。功能总览见[项目架构设计](项目架构设计.md)。

## 1. 先遵守的共同约束

- 先读取工作区改动、`AGENTS.md`、相关源码、资产和证据，再开始修改。
- 保留已有参数、算法、材质入口、资产和工具。参数改名、单位变化、默认值变化都需要明确的兼容方案。
- 窗口布局和样式按用户要求维护；不能借新增效果顺便重做 Outline 窗口。
- 优先使用 UE 材质节点；重复计算先封装成材质函数。只有节点确实不适合时才引入额外着色代码或渲染阶段。
- 先保证基础颜色、法线和原有自发光，再叠加新效果。应用新材质不会自动复制任意原材质图。
- 参数中的 0 有效；“取消本层覆写、恢复继承”表示删除本层设置，不表示写入 0。
- 未经本轮明确要求，不提交、推送、修改引擎或改写 Git 历史。

## 2. 各模块与职责的开发指南

### 工程宿主与配置

入口在 `Source/`、`.uproject` 和 `Config/`。宿主负责加载插件，不应复制插件业务。引擎安装路径由本机参数提供，不写入共享源码。当前记录基于 UE 5.8.3 / CL 58210709；更换版本、渲染设置或平台需要重新核对能力。

屏幕描边依赖 `r.CustomDepth=3`。Substrate 配置会影响表面材质；修改它们要同时说明影响范围，不能仅靠文档构建证明画面正确。

### NPRRuntime：运行时公共部分

这个模块必须能在游戏运行时使用。当前只依赖 Core、CoreUObject 和 Engine；不要加入编辑器窗口、资产创建和关卡保存依赖。临时资源在需要时建立，在结束或切换时正确释放。

### 参数、风格数据和映射

依据 `Documentation/Schemas/` 和公开 C++ 声明。新增参数要写清名称、用途、单位、硬范围、建议范围、默认值、适用对象和与其他参数的关系。

统一外观参数与材质参数分别管理。现有通用覆写结构仍以标量为主，不能把颜色硬塞进一个浮点数。完整风格解析尚未完成，不能假设改 JSON 就会改变场景。

### 材质绑定

入口为 `NPRStyleBindingComponent`。先检查全部目标槽，再创建和应用材质实例；失败不能让部分槽已更新、部分槽未更新。后续调参复用已绑定的 MID，不重复应用整个包。

如果其他系统已经替换材质，恢复操作应保留外部修改。绑定组件不修改 ToonProfile 设置，不把“绑定成功”当成渲染验收通过。

### Surface 材质组合

入口为 `NPRSurfaceRecipe` 和插件 `Content/Surface`。继续采用母材质家族与预制组合说明，不为每一种效果开关组合复制整套材质。

每个效果要有独立参数归属、输入、输出和合成规则。扩展时保留基础自发光和已有 Rim 的贡献；同一材质槽使用兼容的同一个 MID。Recipe 会检查参数类型、唯一归属、依赖和 Rim 固定映射，但不会证明任意材质图的实际算法正确。

原生 MID 接口不会自动校验新 Surface 数值的项目硬范围。调用方需要按 `Documentation/Surface/SurfaceContract.v1.json` 检查。MatCap 和风格化高光仍是后续工作。

### Rim Light

继续复用 `MF_RimLight`、`FNPRRimParameters` 和 `SetRimParameters`。保留四项中文材质参数及默认值：8°、2°、强度 0、白色。程序角度用弧度，写入材质前转换为度数，不能重复转换。

四项值和所有目标槽先通过检查，再一起写入。不得把当前自发光亮边描述成已受真实灯光方向和投射阴影控制。算法与用法见 [Rim Light 介绍](rim_light_introduction.md)。

### Outline 运行逻辑与材质

继续保留整角色和旧单槽入口。Screen 使用像素宽度，反向壳使用厘米宽度，不能改成一个含义模糊的共同数值。

局部设置按“角色 → 组件 → 材质槽 → Section”逐层替换勾选字段。Section 是网格的一块绘制区域，目前只支持单 LOD 且独占材质槽；LOD 是随距离选择的模型精细程度。共享槽和多 LOD 情况应明确拒绝，不能猜测对应关系。

保持深度、区域编号和辅助网格的所有权检查；不覆盖源组件已有的区域标记。切换方法、关闭描边和重新打开关卡后，都要检查没有残留资源。

新增边缘类型前，先证明后端真的能识别它。当前没有自动折痕分类；Screen 不支持连续顶点色或贴图宽度控制。新增宽度和遮罩功能不能直接沿用旧时间稳定性报告作为通过证明。

### NPREditor：窗口、预览与保存

窗口和脚本复用 `NPROutlineEditorLibrary` 服务，避免两套转换逻辑。需要修改关卡或资产的操作应支持编辑器撤销，并显示失败原因。

原材质对比应保持同一模型、相机和灯光。材质槽隔离只是预览状态，不应改变源网格或关卡可见性。预览参考姿势不等于动画验收。

基础预设与角色局部配置分别保存；图片导出不能代替保存关卡。Rim 占位页没有实际参数控制，接入前不得在使用说明中写成可用。

### 角色资产与导入

保留原模型、原材质和纹理来源。不同角色的材质槽不能直接按同一个编号套用。法线贴图需先确认编码和导入设置，不凭文件名猜测。第三方角色的授权和分发限制继续适用，见 `Documentation/GitHubBackup.md`。

### Tools 与验证

资产创建工具只处理明确归属本项目的资产，已有美术修改不能被重建脚本静默覆盖。检查工具尽量只读。修改创建脚本不表示实际二进制资产已经更新。

图像捕获需要确认材质和纹理已完成编译，避免把默认材质当成成功结果。使用独立测试场景，不向用户关卡加入临时测试对象；保留失败尝试和最终通过结果的区别。

### 文档与 OpenSpec

`Documentation/` 保存五份独立说明原文，`docs/` 保存网页页面并同步这五份内容；`openspec/specs/` 负责已有行为和可检查的要求；`openspec/changes/` 只记录真实进行中的变更。已有功能不能仅因为示例目录叫 `add-rim-light` 就被重新列为未完成开发。

OpenSpec 配置引用本轮五份文档。后续写计划时仍需实际读取相关正文、源码和证据；配置中的路径不会自动把整篇内容装入所有命令。OpenSpec 格式校验也不能替代 UE 构建和图像验证。

## 3. 推荐的开发顺序

1. 说明希望改变的画面、支持对象和不处理的范围。
2. 核对当前能力；使用 OpenSpec 时先阅读已有规范和相关变更。
3. 固定参数与组合规则，确认不会破坏原材质和旧接口。
4. 实现最小可工作的渲染与绑定，再接窗口、保存和恢复。
5. 检查源码、参数契约、创建脚本、实际资产和真实画面。
6. 更新对应使用说明、功能状态和更新记录，再运行适用检查。

## 4. 构建与检查

需要完整构建时先保存工作并关闭占用旧模块的编辑器，然后使用自己的引擎目录：

```powershell
./Tools/Build-PrincipledNPR.ps1 -EngineRoot '你的UE5.8目录' -GenerateProjectFiles
./Tools/Build-PrincipledNPR.ps1 -EngineRoot '你的UE5.8目录' -Target Editor
./Tools/Build-PrincipledNPR.ps1 -EngineRoot '你的UE5.8目录' -Target Game
```

按改动选择检查，不把所有检查混成一个“通过”：

| 改动 | 至少检查 |
| --- | --- |
| 文档、文档链接或参数说明 | `npm run docs:generate`、`npm run docs:check`、`npm run docs:build` |
| 语义草案 | `python Tools/verify_semantic_drafts.py`；它不是完整渲染验收 |
| OpenSpec 规范 | `openspec validate --all --strict --no-interactive` |
| Rim 接口或算法 | Game/Editor 构建、相关契约检查及 `NPR.Rim` 自动化；图像用例使用隔离目录以保留旧证据 |
| Surface 接口或图 | Game/Editor 构建、实际资产审查及 `NPR.Surface` 自动化 |
| Outline 渲染、窗口或保存 | 对应的资产、图像、界面和新进程重开检查；按改动范围选择已有工具 |
